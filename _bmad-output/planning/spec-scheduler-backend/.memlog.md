- (direction) Distill README.md on the express path. User asked for a spec alongside the PRD and named _bmad-output/planning/.
- (capability) CAP-1 intent: caller can list events. success: every stored event is returned.
- (capability) CAP-2 intent: caller can create an event. success: a later list includes it.
- (capability) CAP-3 intent: caller can edit an event. success: a later read shows the edited values.
- (capability) CAP-4 intent: caller can cancel an event. success: a cancelled event no longer counts as a conflict.
- (capability) CAP-5 intent: caller can check a proposed event for conflict. success: overlapping active events or unavailable contact time are reported and not stored as a successful create.
- (capability) CAP-6 intent: caller can list contacts. success: every stored contact is returned.
- (capability) CAP-7 intent: caller can create a contact. success: a later list includes it.
- (capability) CAP-8 intent: caller can delete a contact. success: a later list omits it.
- (capability) CAP-9 intent: caller can add or update a contact's availability. success: a later conflict check uses the new availability.
- (capability) CAP-10 intent: caller can record a log. success: the log is stored and can be retrieved. Retrieval shape is open.
- (constraint) Caller-facing communication is gRPC only. README prose overrides the ASCII tree's HTTP handlers.
- (constraint) MySQL is the system of record. Redis is a cache and must not be the only copy of an event or availability.
- (constraint) Event and availability stay consistent: two successful bookings of the same contact time are not allowed.
- (constraint) No UI and no authentication in this service. Peak load to hold is about 120 requests/s. More than one instance must be able to serve.
- (decision) Non-goals: UI, auth, replacing the main application.
- (assumption) Events have a time range and belong to a contact. Cancel is distinct from delete. Conflict means time overlap with an active event or with missing availability.
- (question) Latency number for lookup; conflict rule; event and contact fields; whether delete cascades; what a log contains and whether it must be readable.
- (event) Self-validate pass 1 coherence: capabilities have intent and success; constraints rule out HTTP-as-product, cache-as-source-of-truth, double-booking, UI, and auth. Pass 2 preservation: README operations, NFRs, gRPC, MySQL, Redis, 120 req/s, and no UI/auth landed in the kernel or addendum.md. ASCII tree HTTP handlers recorded as non-target.
- (constraint) Event lookup p99 is under 50 ms. User confirmed. Supersedes the open latency question.
- (constraint) A read matches the last successful write. Cached event or availability must not be older than that write. User confirmed.
- (decision) Event fields are title, capacity, date, start time, and end time. User confirmed. Supersedes the time-range assumption. Contact on an event remains open.
- (decision) A contact is a person with name, email, and phone. User confirmed. Event-to-contact link remains open.
- (decision) Every event has one organizer contact and may have many participant contacts. User confirmed. Conflict subject remains open.
- (constraint) No gap is required between events. An exact endpoint touch is not a conflict. User confirmed.
- (constraint) A conflict counts both the organizer and the participants. User confirmed.
- (decision) Contact delete is a status change to inactive. Rejected when the contact has a future event, judged by start time, as organizer or participant. User confirmed.
